# 工程准则

PRD、实现、审查、顾问共用这一份标准。仓库自身规范与本准则冲突时，以仓库规范为准。

## 设计

- **从第一性原理出发。** 先写清要解决的问题、必须成立的不变量、数据形状，再选方案。不在现有补丁上叠补丁。新需求按“如果一开始就有这个需求，该怎么设计”来改。
- **优先用成熟方案。** 选型先找业界公认的做法：语言和框架的官方推荐、主流大厂开源的成熟架构、标准库。PRD 写明采用的方案和依据。没有充分理由不自创。
- **不走旁路。** 按框架和库设计的用法写。不用替代实现、猴子补丁、反射、私有 API 绕开问题。确实被上游 bug 卡住时，选最直接的规避方式，原因写进 commit message，不写在代码注释里。
- **状态只存一份。** 不引入要和主数据保持同步的第二份状态，例如快照、镜像、独立缓存的基线。能从主数据算出来的就现算。
- **不做向后兼容。** 改接口、载荷、枚举、存储结构时，直接改并在同一次改动里迁移所有调用方。不保留旧接口、兼容分支、转发层、别名、废弃标记，也不为部署前的旧数据写兼容代码。只有用户明确要求兼容时才做。跨仓库的契约两边一起改。
- **不过度设计。** 没有当前使用方的抽象层、扩展点、插件机制、配置开关、特性开关都不加。一个职责只在一处实现。不加 PRD 没要求的监控、埋点、重试、缓存、限流。

## 实现

- **错误要暴露。** 只捕获已识别、有明确处理方式的预期错误，并转成业务结果。其余异常向上传播到框架或事务边界统一处理。不整体包 `try/except`，不写把错误伪装成成功或默认值的兜底，不吞异常后只打日志。
- **修根因。** 从症状追到第一个出错的地方，在那里修。只有当被处理的状态本身是合法状态时，加防御判断才算修复。
- **规则写进代码结构。** 能用类型、命名、枚举、断言表达的约束，不写成注释。注释只留代码无法表达的原因：非直觉的取舍、外部协议约束、事故因果。
- **边界要有类型。** 新增和修改的边界提供完整类型，不用隐式 Any 或裸容器。不放宽检查配置来掩盖本次的类型错误。
- **资源和并发要有所有者。** 每个资源、后台任务、并发任务都有明确的创建者，负责等待、取消、异常处理和释放。
- **副作用放在提交之后。** 依赖数据库写入的外部副作用，例如缓存、队列、消息，在事务提交后执行，并且要幂等。
- **提示词只写改变行为的内容。** 写给模型的每一句，都要答得出“删掉后模型会做错什么”。

## 测试

- 测试可观察的行为，不测内部实现。只替换 I/O 和非确定性依赖，不 Mock 被测逻辑本身。
- 断言业务字段和状态变化，不只看成功标志。失败路径要验证不该发生的写入和副作用确实没发生。
- 不连真实数据库、缓存、生产 API 等共享基础设施。
- 钱、权限、事务、并发、生命周期类改动必须有覆盖相应风险的测试。已有测试充分时复用。

## 范围

- 只做需求要求的。顺手发现的无关存量问题记下来，不在本次修。
- 本次改动暴露出的类型或测试问题，在本次修好。
- 已经通过、且没受后续改动影响的检查不重复跑。

## 审查尺度

- 只报能给出触发路径的问题：什么输入或操作，导致什么错误结果。给不出触发路径的不算缺陷。
- 区分 bug 和取舍。取舍只说一次，不反复论证。
- 用户已经明确否决或拍板的方案，不再当作缺陷提出。
- 违反本准则的写法要报：吞错兜底、向后兼容代码、多余抽象、绕开框架的写法、自创方案却有成熟替代。
- 不以“建议增强”打回，不提议本准则禁止加的东西。
