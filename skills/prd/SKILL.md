# PRD

产出 `.baton/<branch>/PRD.md`，由用户确认后作为后续所有实现和审查的唯一依据。

## 1. 开工

1. 根据需求定一个分支名，惯例看 `git branch -r` 和 `git log`。
2. 每个涉及的仓库跑 `${CLAUDE_PLUGIN_ROOT}/scripts/start.sh <branch> [base]`，跨仓库时分支同名。脚本从最新远端基线切分支、取消 upstream、建好 `.baton/<branch>/`，并把 `.baton/` 写进 `.git/info/exclude`，所以这些文件不会进 PR。
   基线默认 `dev`，没有 `dev` 时用远端默认分支。工作区不干净时脚本会退出，先问用户怎么处理已有改动。

## 2. 收集

- 读需求涉及的代码、接口、数据模型、调用方和现有测试，弄清现状。
- 读仓库上下文：规范入口（`AGENTS.md`、`CLAUDE.md`、`.claude/rules` 等）和相关用户记忆；测试、类型检查、lint 命令和解释器路径；提交钩子要求和 commit 惯例；规范点名的高风险领域；规定的收尾审查步骤。
- 能从代码或运行结果确定的，自己查清。只有产品取舍类问题（要不要做、对用户表现成什么样）才问用户，一次问完。其余不确定的写成假设。

## 3. 起稿

`PRD.md` 结构如下，不适用的节写“无”，不要删：

1. **目标。** 谁遇到什么问题，做完后他们能观察到什么变化。
2. **范围。** 做什么、明确不做什么。
3. **行为。** 用户可见的流程、接口契约、状态变化、错误表现。
4. **技术方案。** 数据形状先行，然后是改动的模块、接口、存储和迁移。跨仓库时写清各仓库的契约。新项目把技术栈选型写在这里。
5. **风险。** 哪些部分属于高风险，原因是什么。
6. **验收标准。** 逐条编号，每条可由测试、命令或可观察行为验证。
7. **假设。** 查不到而采用的推荐方案。
8. **仓库上下文。** 第 2 步收集的规范入口、检查命令、提交要求、高风险范围、收尾审查。

只写会影响实现或验收的内容。

## 4. 交叉验证

把 Codex 说明写到 `.baton/<branch>/reviews/PRD.prompt.md`，执行：

```bash
${CLAUDE_PLUGIN_ROOT}/scripts/review.sh .baton/<branch> PRD 3
```

说明要点：PRD 路径和需求原文；对照代码找遗漏、内部矛盾、与现有代码冲突的地方，以及无法验证的验收标准；每条给出会导致什么错误结果；不提额外功能。`location` 填章节号或代码位置。

逐条判断结论。成立的改进 PRD，不成立的写进假设节说明理由。复审时改写 prompt 文件说明改了什么，再跑同一命令。退出码 0 通过，2 打回，3 达到上限，此时把剩余分歧写进假设节。

## 5. 定稿

给用户一份摘要：目标、范围、关键技术决定、验收标准、假设、Codex 提出但没采纳的意见。用户确认或修改后更新 PRD，在文件首行写 `状态：已确认 <日期>`。

这是整个流程中唯一一个需要等用户回复的环节。确认之后，如果是从 build 进来的，直接回到 build 继续。
