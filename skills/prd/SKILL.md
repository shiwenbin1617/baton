# PRD

把用户的需求变成 `.baton/<branch>/PRD.md`：一份基于代码现实、经过另一个模型交叉验证、由用户确认过的文档。确认后，它是后续实现、审查和验收的唯一依据。

需求：$ARGUMENTS

## 原则

- **先查后问。** 能从代码、文档、运行结果确定的事自己查清楚。只有产品取舍才问用户：要不要做、对用户表现成什么样、优先级如何。
- **一次问完。** 需要问用户时把问题集中成一个清单，每个问题附上你的推荐答案。
- **方案从本质出发。** 先写清问题本质和不变量，再选方案。每个选型写明采用的成熟方案和依据。
- **只写有用的。** 每一节只写会影响实现或验收的内容。

## 资源

- `${CLAUDE_PLUGIN_ROOT}/references/engineering.md`：工程准则，起稿前读。
- `${CLAUDE_PLUGIN_ROOT}/references/prd-template.md`：PRD 模板。
- `${CLAUDE_PLUGIN_ROOT}/references/briefs.md`：其中“PRD 交叉验证说明”是 Codex 的说明模板。
- `${CLAUDE_PLUGIN_ROOT}/scripts/start.sh <branch> [base]`：切分支，建工作目录。
- `${CLAUDE_PLUGIN_ROOT}/scripts/review.sh <workdir> <id> [max-rounds]`：Codex 只读审查，续接同一会话。退出码 0 通过，2 打回，3 达到上限。

---

## 阶段 1：开工

**目标：** 在干净的新分支上建好工作目录。

**动作：**
1. 从需求里解析出基线参数 `base=<分支>`。没写就交给脚本处理：默认 `dev`，没有 `dev` 时用远端默认分支。
2. 按仓库惯例起分支名，参考 `git branch -r` 和 `git log --oneline -20`。
3. 判断涉及哪些仓库。跨仓库时每个仓库都跑一次，分支同名。
4. 在每个仓库根目录运行 `start.sh <branch> [base]`。脚本会从最新远端基线切分支、取消 upstream、建立 `.baton/<branch>/`，并把 `.baton/` 写进 `.git/info/exclude`，这些文件不会进 PR。
5. 脚本因工作区不干净退出时，停下来问用户如何处理已有改动。不要 stash 或丢弃用户的改动。

---

## 阶段 2：调研

**目标：** 弄清现状和约束，足以写出不靠猜的方案。

**动作：**
1. 读需求涉及的代码：入口、数据模型、接口、调用方、已有测试。找到仓库里最相近的已有实现，作为方案参照。
2. 收集仓库上下文：
   - 规范入口：`AGENTS.md`、`CLAUDE.md`、`.claude/rules`、`CONTRIBUTING.md` 等。
   - 测试、类型检查、lint 命令和解释器路径，来自仓库配置、CI 文件和用户记忆。
   - 提交钩子要求和 commit 惯例，来自钩子配置和 `git log`。
   - 仓库规范点名的高风险领域，和规定的收尾审查步骤。
   - 用户记忆里与本需求相关的已拍板取舍和否决过的方案。
3. 选型时找成熟方案：语言和框架的官方推荐做法、主流开源项目的通行架构、仓库里已经验证过的同类实现。需要时查官方文档。
4. 列出仍不确定的点，分成两类：产品取舍类问用户，其余写成假设。

---

## 阶段 3：起稿

**目标：** 写出完整的 PRD 草稿。

**动作：**
1. 读工程准则，再按 PRD 模板写入 `.baton/<branch>/PRD.md`，首行 `状态：草稿`。
2. 技术方案按顺序写：问题本质和不变量、数据形状、选型表、改动清单、跨仓库契约。
3. 涉及接口或存储变更时，写明所有调用方如何在同一次改动里迁移。用户没有要求兼容时不留兼容层。
4. 验收标准逐条编号，每条都能用测试、命令或可观察行为验证。
5. 风险节标出高风险部分。这些条目到 build 阶段由主控亲自实现。
6. 跨仓库时每个仓库各放一份 PRD，契约部分保持一致。

---

## 阶段 4：交叉验证

**目标：** 让另一个模型找出遗漏、矛盾和更好的现成做法。

**动作：**
1. 按“PRD 交叉验证说明”模板写 `.baton/<branch>/reviews/PRD.prompt.md`。
2. 运行 `${CLAUDE_PLUGIN_ROOT}/scripts/review.sh .baton/<branch> PRD 3`。工程准则会自动拼在说明前面。
3. 逐条判断结论：
   - 成立的：修改 PRD。
   - 不成立的：把理由写进假设节。
4. 退出码 2 时，按复审模板改写 prompt 文件，再跑同一命令。
5. 退出码 3 时，把剩余分歧写进假设节，带到用户确认环节。

---

## 阶段 5：用户确认

**目标：** 由用户拍板，PRD 定稿。

**动作：**
1. 给用户一份摘要：目标、范围（含不做什么）、关键技术决定及依据、验收标准、假设、Codex 提出但没采纳的意见及理由，以及需要用户决定的问题和你的推荐。
2. 等用户回复。这是整个 baton 流程中唯一要等用户的环节。
3. 按用户意见更新 PRD，首行改成 `状态：已确认 <YYYY-MM-DD>`。
4. 如果是从 baton:build 进来的，回到 build 继续，不再等待。
